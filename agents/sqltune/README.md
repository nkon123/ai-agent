# sqltune (SQL 튜닝 진단)

느린 쿼리를 **오라클 튜닝 기준**으로 진단하고, 실행계획을 보고, 인덱스를
제안한다. 필요하면 실제로 수행해 시간과 실제 계획까지 비교한다.

```
안전 검사 → 정적 규칙 → 실행계획(EXPLAIN) → 플랜 규칙
→ 인덱스 제안 → (선택) 실제 수행 비교 → (선택) LLM 개선안
```

## 실행

```bash
python agents/sqltune/agent.py -f slow.sql
python agents/sqltune/agent.py -q "SELECT * FROM ORD_HDR WHERE ..."
python agents/sqltune/agent.py -f slow.sql --run       # 실제 수행까지 비교
python agents/sqltune/agent.py -f slow.sql --compare   # 개선 후보 생성·비교
python agents/sqltune/agent.py -f slow.sql --count     # 결과 건수까지 비교
python agents/sqltune/agent.py -f slow.sql --json      # 기계용
```

```
[진단] 문제 4건
  - func-on-column     인덱스 컬럼에 함수를 씌우면 인덱스를 타지 못한다
      근거: WHERE TO_CHAR(REG_DT,'YYYYMMDD')='20260101'
  - negation           부정 조건은 인덱스로 걸러내지 못한다
  - select-star        필요한 컬럼만 적으면 커버링 인덱스로 …
  - literal-value      리터럴만 쓰면 하드파싱이 반복된다

[실행계획]
 Id Operation                    Object          Rows     Cost
───────────────────────────────────────────────────────────────
  0 SELECT STATEMENT                            100000     842
  1  SORT ORDER BY                              100000     842
  2   TABLE ACCESS FULL         ORD_HDR         100000     840

[인덱스 제안] 등치 1개 · 범위 1개 · 정렬 1개 순으로 구성했다
  CREATE INDEX IX_ORD_HDR_STATUS_REG_DT ON ORD_HDR (STATUS, REG_DT, ORD_NO);
  ※ 실행하지 않았다. 검토 후 직접 수행할 것
```

## 바인드 변수가 있는 쿼리

실무 쿼리는 대부분 바인드를 쓴다. 단계마다 필요한 것이 다르다.

| 단계 | 바인드 값 | 왜 |
|---|---|---|
| 정적 진단 | 필요 없음 | 본문만 본다 |
| **실행계획** | **필요 없음** | EXPLAIN PLAN 은 바인드 값을 보지 않는다 |
| 건수·수행 | **필요함** | 값이 없으면 조건이 맞지 않아 0건이 나온다 |

```bash
python agents/sqltune/agent.py -f slow.sql \
    --bind if_key=EAIIF0001234 --bind dt=20260101 --count --run
```

값을 안 주고 `--count`/`--run` 을 쓰면 실행하지 않고 알려 준다.

```
[확인 필요] 바인드 값이 없어 건수·수행 비교를 건너뛰었다 (:if_key, :dt).
           --bind 이름=값 으로 넘길 것
```

NULL 로 채워 돌리면 0건이 나오는데 그걸 "빠르다"로 읽으면 잘못된 결론이 된다.
실행계획 비교는 값 없이도 그대로 된다.

> **ORA-01036 (illegal variable name/number)**
> EXPLAIN PLAN 문에 대상 SQL 의 바인드가 그대로 들어가는데 값을 안 넘겨서
> 났던 오류다. 이제 바인드 이름을 뽑아 값을 채워 넣는다.
> `statement_id` 도 바인드로 넘기지 않는다 — 대상 SQL 의 바인드와 섞여
> 같은 문제를 일으킨다.

## 판정 기준은 문서 한 곳에

`agents/sqltune/tuning_rules.md` 가 기준이다. **규칙 엔진과 LLM 프롬프트가
같은 문서를 본다.** 기준을 코드에 흩어 놓으면 한쪽만 고쳤을 때 서로 다른
답이 나온다. 사내 기준이 다르면 `config.SQLTUNE_RULES_FILE` 로 바꾼다.

규칙명(`func-on-column`, `full-scan` …)은 문서와 코드가 같은 이름을 쓴다.
결과에 규칙명이 찍히므로 "왜 이렇게 판정했나"를 문서에서 바로 찾을 수 있다.

## 안전 (이 에이전트에서 특히 중요하다)

| 규칙 | 이유 |
|---|---|
| **SELECT 만 받는다** | DML/DDL/PL-SQL 블록/`FOR UPDATE`/`UTL_`·`DBMS_` 패키지 호출을 거부한다. 튜닝 도구가 데이터를 바꾸면 사고다 |
| **한 문장만** | 세미콜론 뒤에 내용이 있으면 거부한다 |
| **인덱스는 제안만** | `CREATE INDEX` 를 만들어 보여줄 뿐 실행하지 않는다 |
| **실행은 기본 꺼짐** | 실행은 곧 운영 DB 부하다. CLI `--run` 으로 사람이 켤 때만. **MCP 툴은 어떤 설정에서도 실행하지 않는다** |
| **읽기 상한** | 실행 시 `SQLTUNE_MAX_ROWS`(기본 100)행·`SQLTUNE_TIMEOUT_SEC`(기본 60초) |

안전 검사는 **주석과 문자열을 지운 사본**으로 한다. 원문으로 검사하면
`SELECT 'DELETE ME' FROM dual` 이 DML 로 오탐되고, 반대로 주석에 가린
것을 놓친다.

## 실행 비교 (`--run`)

`GATHER_PLAN_STATISTICS` 힌트를 붙여 수행하고 `DBMS_XPLAN.DISPLAY_CURSOR`
로 **실제** 계획을 받는다. 추정(E-Rows)이 아니라 실제(A-Rows)를 본다.

- **Buffers(논리적 읽기)를 먼저 본다.** 수행 시간은 캐시·부하에 흔들리지만
  Buffers 는 재현된다
- `SQLTUNE_RUNS`(기본 2)회 수행하고 **최소값**을 쓴다. 첫 회에는 하드파싱과
  캐시 적재가 섞인다
- 상한까지만 읽었으면 "실제 수행 시간은 더 길 수 있다"고 결과에 남긴다

같은 세션에서 실행 → `DISPLAY_CURSOR` 순으로 부른다. 다른 세션에서는 방금
그 커서를 볼 수 없다.

## 인덱스 제안 규칙

등치(`=`) → 범위(`>`, `BETWEEN`, `LIKE 'x%'`) → `ORDER BY` 순으로 컬럼을
배치한다(기준 문서 7항). **기존 인덱스의 선두 컬럼이 같으면 제안하지
않는다** — 중복 인덱스는 조회를 빠르게 하지 않고 DML 만 느리게 한다.

조건을 못 찾으면 억지로 만들지 않고 "확인 필요"로 남긴다. 정규식 기반이라
완벽하지 않고, 어차피 사람이 검토할 제안이다.

## 사고 과정(thinking)은 끈다

후보 생성은 **사고 과정을 끄고** 부른다. 켜 두면 사고에만 수백 초를 쓰고
정작 본문이 비어 나온다.

```
사고 켬 → 392초 후 빈 출력 → OutputParserException: Invalid json output
사고 끔 → 12초, 후보 2개 정상
```

판정 과제인 `impact` 는 반대로 **켜 둔다** — 거기서는 사고가 정확도를
크게 올린다(같은 3건에서 3/3 대 1/3). 과제 성격이 다르다.

기준 문서도 통째로 넣지 않고 **걸린 규칙만** 추려 보낸다(2,158자 → 430자).
LLM 은 우리가 찾은 문제를 고치는 역할이지 문서를 통독할 이유가 없다.

## LLM 역할

기준 문서와 **규칙이 찾은 문제**를 함께 주고 고친 쿼리를 받는다.
LLM 이 규칙 판정을 뒤집지 않는다 — 근거로 삼을 뿐이다.
`USE_LLM=false` 면 규칙 진단까지만 하고 끝난다.

## MCP

| 툴 | 등급 | 무엇 |
|---|---|---|
| `tune_query(sql)` | combo | 진단 + 인덱스 제안 (**실행 안 함**) |
| `explain_query(sql)` | step | 실행계획만 |

리소스는 두지 않았다. 다른 에이전트는 키(짧은 문자열)로 상세를 다시 읽지만
여기서는 입력이 SQL 전문이라 URI 에 담을 수 없다. 전체 결과가 필요하면
CLI 를 쓴다.

## 후보 비교 (`--compare`, `--count`)

LLM 이 기준 문서를 근거로 개선 후보를 만들고, 원본과 **같은 기준으로 재서**
순위를 매긴다.

```
  후보          Cost        건수     시간(초)   Buffers  비고
  ──────────────────────────────────────────────────────────────────────
  원본           900      1204     3.020     50000
  후보1           12      1204     0.210       220  TO_CHAR 제거 → 범위 조건
  후보2            4       100     0.020        30  결과 건수가 다르다
                                                    (원본 1204건 → 100건)
                                                    — 튜닝이 아니라 버그다

  → 가장 나은 것: 후보1
```

**후보2는 모든 수치에서 가장 빠르지만 탈락한다.** 건수가 달라졌기 때문이다.
빠른 게 아니라 덜 한 것이다.

| 옵션 | 하는 일 | 비용 |
|---|---|---|
| (없음) | 원본만 진단 | LLM·DB 모두 안 씀 (플랜만) |
| `--compare` | 후보 생성 + 플랜(Cost) 비교 | LLM 1회. 후보마다 EXPLAIN |
| `--count` | 위 + **결과 건수 비교** | 원본·후보를 각각 `COUNT(*)` 로 감싸 **실행** |
| `--run` | 위 + 수행시간·Buffers 비교 | 원본·후보를 각각 **실행** (기본 2회) |

`--count` 를 따로 켜는 이유: 건수를 세려면 `SELECT COUNT(*) FROM (원본)` 을
실제로 돌려야 한다. 행을 전송하지 않아 결과를 다 받는 것보다는 가볍지만,
**DB 는 원본만큼 일한다.** 운영 DB 에서 무거운 쿼리를 튜닝 중이라면
그 자체가 부하다.

`--count` 없이 비교하면 결과에 이렇게 남는다.

```
[확인 필요] 결과 건수를 비교하지 않았다 — 후보가 같은 결과를 내는지 확인할 것
```

**LLM 이 만든 SQL 도 원본과 똑같은 안전 게이트를 통과해야 한다.**
`DELETE` 를 내놓으면 측정하지 않고 탈락시킨다.

### 무엇을 병렬로 하는가

단계마다 다르다. 전부 옵션으로 끄고 켤 수 있다.

| 단계 | 기본 | 왜 |
|---|---|---|
| **EXPLAIN** | **병렬** | 실행이 아니라 파싱이다. 부하가 거의 없고 왕복 횟수만큼 시간이 준다 |
| **COUNT** | 순차 | 건수는 결정적이라 병렬로 해도 값은 같다. 다만 무거운 쿼리를 동시에 던지는 것이라 **순간 부하가 후보 수만큼** 커진다 |
| **수행시간** | **항상 순차** | 동시에 돌리면 서로 CPU·I/O·버퍼캐시를 뺏어 **재려던 수치가 오염된다** |

```bash
--no-parallel-explain   # 실행계획도 순차로
--parallel-count        # 건수를 병렬로 (빠르지만 피크 부하가 커진다)
--no-interleave         # 교차 반복 끄기
```

수행시간은 어떤 설정으로도 병렬이 되지 않는다. 그건 옵션이 아니라 원칙이다.

### 교차 반복 (기본 켜짐)

수행시간을 잴 때 `원본 → 후보1 → 후보2 → 원본 → 후보1 → 후보2` 순으로 돈다.

끄면 `원본 → 원본 → 후보1 → 후보1 → …` 이 되는데, 그러면 **뒤에 측정한 쪽이
앞 쿼리가 데워 놓은 캐시 덕을 본다.** 같은 쿼리라도 순서만 바꾸면 이기는
일이 생긴다. 교차하면 그 편향이 줄어든다.

각 후보의 값은 여러 회 중 **최소값**을 쓴다(기준 문서 8항).
끄고 쓰면 결과에 "교차 반복 없이 쟀다"는 경고가 남는다.

비교할 때 원본은 **한 번만** 잰다. 예전에는 단독 수행 측정과 비교 측정이
각각 원본을 돌려 느린 쿼리를 쓸데없이 더 실행했다.

### 순위 기준

`Buffers → 수행시간 → Cost` 순으로 본다(기준 문서 8항).
Buffers 를 먼저 보는 이유는 수행 시간이 캐시·부하에 흔들리는 반면 논리적
읽기는 재현되기 때문이다. Cost 는 추정치라 마지막이다.

측정에 실패했거나(EXPLAIN 오류) 탈락한 후보는 순위에서 뺀다.

## 아직 없는 것

- **결과 값 비교** — 건수는 보지만 값까지 대조하지는 않는다. 건수가 같아도
  값이 다를 수 있다(조인 중복, 정렬 차이). 최종 확인은 사람이 한다
- **SQL 파서** — 술어 추출이 정규식이라 서브쿼리·인라인뷰가 섞이면 놓친다
- **PLAN_TABLE 자동 생성** — 없으면 `?/rdbms/admin/utlxplan.sql` 안내만 한다
